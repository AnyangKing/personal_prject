# 공고 모니터 (rfp_watch)

국내외 R&D 과제·사업 공고를 **매일 아침 자동으로 모아 신규 건만** 골라
HTML 리포트와 윈도우 토스트로 알려줍니다.

## 실행

```
python rfp_watch.py              평소 실행 (신규만 리포트)
python rfp_watch.py --site iris  특정 사이트만 시험 실행
python rfp_watch.py --all        신규가 아닌 것도 전부 리포트에 담기
python rfp_watch.py --show       브라우저 창을 띄워 동작 확인 (문제 생겼을 때)
python rfp_watch.py --no-open    리포트를 자동으로 열지 않음
```

작업 스케줄러에 **`공고 모니터`** 라는 이름으로 매일 09:35 실행되도록 등록돼 있습니다.
(콘솔 창이 뜨지 않도록 `pythonw.exe` 로 실행됩니다)

## 설정 바꾸기 — `rfp/config.py`

- `DIRECT_KEYWORDS` : 직결어. **5점** (수중음향, 음향측위, USBL, 소나, 음탐기, 선배열 …)
- `FIELD_KEYWORDS` : 분야어. **3점** (수중, 음향, 해저, 천해, AUV …)
- `NEAR_KEYWORDS` : 인접어. **1점**, 합쳐서 최대 2점 (잠수함, 어뢰, 해양, 통신 …)
- `TOAST_MIN_SCORE` : 이 점수 이상이면 '추천 공고'로 리포트 상단 + 토스트 알림 (기본 3점)
- `EXCLUDE_KEYWORDS` : 제목에 있으면 아예 버림 (채용, 심사결과 …)
- `DETAIL_SITES` : 상세·첨부까지 읽을 사이트
- `MAX_DETAIL_FETCH` : 한 실행에서 열어볼 공고 수 (기본 25)
- `ENABLED_SITES` : 수집할 사이트. 잠시 끄려면 앞에 `#`
- `HIDE_EXPIRED` : 접수 마감이 지난 공고 숨김 (기본 켜짐)

**공고를 놓치지 않도록 키워드로 걸러내지 않습니다.** 신규 공고는 전부 리포트에
싣되 점수로 정렬만 하므로, 키워드를 좁게 잡아도 아래쪽에서 확인할 수 있습니다.

## 키워드는 3단계입니다

연구실 분야(**수중통신 · 수중위치추정**)는 전문 용어가 뚜렷해서, 일반어를 넣으면
신호가 아니라 잡음이 됩니다. 예전에 `국방`이 16건, `通信`이 10건 걸리면서
임계값 3점을 일반어 세 개 조합으로 넘겨버렸습니다.

| 등급 | 점수 | 성격 | 예 |
|---|---|---|---|
| 직결 | 5점 | 나오면 사실상 확정 | 수중음향, 음향측위, USBL, DVL, 소나, 음탐기, 선배열, 다중경로 |
| 분야 | 3점 | 맞는 영역 | 수중, 음향, 음파, 천해, 해저, AUV/ROV/UUV |
| 인접 | 1점 | 같이 나오지만 기술이 아님 | 잠수함, 잠수정, 어뢰, 무인수상정, USV, 해양, 통신 |

**인접어는 합쳐서 최대 2점**입니다. 잠수함은 플랫폼이지 수중통신 기술이 아니므로,
인접어만으로는 임계값을 넘지 못하게 막습니다.

`무인수상정`·`USV`는 **수상**이라 인접으로 둡니다. `6G`·`NTN`·`기지국`·`레이더`·
`해양플랜트`처럼 지상통신·조선업 용어는 아예 뺐습니다.

## 첨부 공고문까지 읽습니다

공고 제목은 대개 **사업명뿐**이고 실제 세부 과제 목록(RFP)은 첨부 HWP 안에 있습니다.
제목만 채점하면 이런 공고가 0점으로 묻힙니다:

```
'26년 착수 민군기술협력사업 RFP 설명회 개최 안내      ← 제목 기준 0점
  └ 첨부 안: DAS 기반 항만감시체계용 광섬유 선배열 소나시스템 개발
             저궤도 상용위성통신 기반 잠수함 위성통신체계 개발
```

그래서 `DETAIL_SITES` 에 지정한 사이트는 상세를 열어 첨부 공고문 본문까지 읽습니다.
지원 형식은 **.hwp(한글 바이너리) · .hwpx · .pdf · .docx · .txt** 입니다.
항목 URL 자체가 문서인 경우(JAMSTEC 공모 PDF)에는 그 파일을 바로 받아 읽습니다.

일본 공고문은 **전각 숫자와 和暦**(`令和８年９月３０日`)을 쓰므로 서기로 변환해 처리합니다.

**사이트가 봇 차단 화면을 띄우면 우회하지 않고 실패로 남깁니다.** 다만 일시적인
상태이므로 재시도 한도를 깎지 않고 다음 실행에서 다시 열어 봅니다. 같은 상세
페이지를 여러 항목이 가리키면 한 번만 요청하고, 요청 사이에 `DETAIL_DELAY_MS`
만큼 간격을 둡니다.

**채점 규칙이 제목과 다릅니다.** 첨부 본문에서는 **인접어를 아예 세지 않고**
직결(4점)·분야(2점)만 셉니다. 수만 자짜리 공고문에 '잠수함'이 몇 번 나오는 건
아무 의미가 없기 때문입니다 — 실제로 채용 공고 첨부에 '잠수함'이 4회 나와
오탐이 났습니다. 직결·분야가 2종류 미만이면 첨부 점수를 주지 않습니다.

또한 **첨부 점수는 직결어를 요구합니다.** 직결어가 하나도 없으면 분야어가
3종 이상 나와야 인정합니다. 6만 자 문서에 분야어 두 개가 흩어져 있는 건
제목에 `수중`이 박힌 것(3점)보다 약한 증거이기 때문입니다.

**임계값 3점의 의미:** 제목에 분야어 하나(`수중`·`음향`·`해저`·`AUV`)만 있어도
추천에 올립니다. 인접어는 합쳐서 최대 2점이라 아무리 모여도 추천이 되지 않습니다.

- 한 번 읽은 공고는 `data/rfp_detail.json` 에 남아 **다시 받지 않습니다**
- 한 실행에서 여는 수는 `MAX_DETAIL_FETCH`(기본 25)로 제한하고, 남은 것은 다음 실행에서 이어서
- **첨부를 읽지 못한 공고는 리포트의 '직접 확인 필요' 구역**에 따로 올립니다
  (점수를 믿을 수 없으므로 묻히지 않게)
- 읽기에 **실패한 공고는 `DETAIL_RETRY`(기본 3)회까지 다시 시도**합니다
  (일시적 네트워크 오류로 영구 포기하지 않도록)
- `--no-detail` 로 끄면 빠르게 돕니다

## 감시 페이지 (연 1회 공모)

ATLA·JSPS 처럼 **연 1회 공모**를 내는 곳은 새 글이 올라오는 게 아니라
**같은 주소의 페이지 내용이 바뀝니다.** '새 글번호 = 신규' 방식으로는
공모가 열려도 알 수가 없습니다.

그래서 본문을 `data/rfp_pages.json` 에 저장해 두고 다음 실행에서 비교합니다.
새로 생긴 줄이 있으면 **그것을 하나의 공고 항목으로 만들어** 기존 채점·리포트·
알림 흐름에 그대로 태웁니다.

- 항목 id 에 변경분의 해시가 들어가므로, **같은 변경으로 두 번 알리지 않습니다**
- 변경분이 채점 대상이라 `水中音響` 이 새로 등장하면 바로 점수를 받습니다
- 리포트에 **무엇이 바뀌었는지 그 줄을 그대로** 보여 줍니다
- 첫 실행은 기준선만 저장하고 알리지 않습니다
- 조회수·타임스탬프처럼 매번 달라지는 것은 비교에서 제외합니다
- 봇 차단 화면이 뜨면 기준선을 덮어쓰지 않고 건너뜁니다

감시 대상은 `config.WATCH_PAGES` 에서 바꿉니다. `--no-watch` 로 끌 수 있습니다.

실제 동작 예 (ATLA 공모가 열렸다고 가정):
```
[내용 변경] ATLA 안전보장기술연구추진제도 공모        8점  ★추천
  · 令和９年度 安全保障技術研究推進制度の公募を開始しました。
  · 研究テーマ： 水中音響を用いた目標識別技術
  · 水中通信ネットワークの高信頼化に関する研究
  근거: 水中音響, 水中通信 / 마감 2027-03-17
```

## 마감일 추정

KRIT·DAPA·ICMTC 게시판은 목록에 마감일 컬럼이 아예 없습니다. 접수기간은
공고문 안에 있으므로, 이미 받아 둔 첨부 본문에서 뽑아냅니다.

- HWP 표는 `접수기간 :` 라벨과 날짜가 다른 줄로 쪼개지므로 **앞줄까지 문맥으로** 봅니다
- 이메일·URL·전화번호·시각은 먼저 지웁니다
  (`a07-10186@mnd.go.kr` 의 `07-10` 이 7월 10일로 읽힌 적이 있습니다)
- 기간이면 **읽는 순서상 마지막** 날짜가 마감입니다
- `입장·참석·통보·점검` 같은 동작을 가리키는 '까지'는 버립니다
  (`설명회 장소에 입장 ... 까지` 가 마감일로 잡힌 적이 있습니다)

**추정값으로는 지우지 않습니다.** 잘못 읽으면 살아 있는 공고가 사라지기
때문입니다. 화면에 `마감(추정)`으로 점선 표시하고, 마우스를 올리면 근거 문장이
보입니다. 목록에서 받은 확정 마감일만 필터에 씁니다.

## 내 관심 공고 (별표)

리포트의 각 공고 오른쪽 `☆` 를 누르면 화면 오른쪽 **내 관심 공고** 패널에 모입니다.

- 별표는 브라우저 localStorage 에 남으므로 **다음날 리포트에도 그대로 따라옵니다.**
- 패널은 **마감이 가까운 것부터** 정렬되고, 마감된 것은 흐리게 맨 뒤로 갑니다.
- 공고 제목·링크·마감일을 함께 저장하므로, 그 공고가 더 이상 신규가 아니어도
  패널에서는 계속 보입니다.
- 패널의 `✕` 로 뺄 수 있습니다.

'추천 공고'(키워드 점수로 자동 선별)와 '내 관심 공고'(직접 지정)는 별개입니다.

**주의:** 별표는 브라우저별로 저장됩니다. Chrome에서 지정한 것이 Edge에는 없습니다.
옮기거나 백업하려면 패널 아래 `백업 보기` 로 JSON을 복사해 두고,
다른 브라우저에서 `붙여넣어 복원` 을 쓰세요.

## 사이트 개편 감지

사이트가 HTML 구조를 바꾸면 **에러가 나지 않고 그냥 0건이 반환됩니다.**
그대로 두면 몇 달째 못 받고 있어도 알 수 없으므로, 사이트별 최근 7회 수집량을
`data/rfp_health.json` 에 남기고 그 중앙값과 비교합니다.

| 조건 | 판정 |
|---|---|
| 오늘 0건 + 평소 1건 이상 | 수집 실패 의심 (며칠째인지 함께 표시) |
| 평소 5건 이상인데 오늘 40% 미만 | 건수 급감 — 목록 일부만 읽힘 |
| 이력 없음 (첫 실행) | 판단 보류 |

비교는 **마감 필터를 거치기 전의 파싱 건수**로 합니다.
(NTIS처럼 100건 받아 대부분 마감으로 걸러지는 건 정상이므로)

걸리면 리포트에 **점검 필요** 섹션이 뜨고 토스트에도 `(수집 이상 N곳)` 이 붙습니다.
그때 `--show` 로 해당 사이트만 돌려 보면 무엇이 바뀌었는지 확인할 수 있습니다.

기준값은 자동으로 학습되므로 사이트를 추가해도 따로 설정할 게 없습니다.

## 파일 구조

```
rfp_watch.py        진입점
rfp/config.py       설정 (여기만 고치면 됩니다)
rfp/score.py        관심도 채점
rfp/store.py        본 공고 기록 (신규 판별)
rfp/report.py       HTML 리포트 생성
rfp/fetch.py        브라우저·날짜 파싱 공용
rfp/board.py        단순 목록형 게시판 공용 수집기
rfp/health.py       사이트 개편 감지
rfp/sites/*.py      사이트별 수집 모듈
data/rfp_seen.json  이미 본 공고 (지우면 전부 신규로 잡힙니다)
data/rfp_health.json 사이트별 수집량 이력 (개편 감지용)
data/rfp_detail.json 첨부를 읽은 공고 기록 (재다운로드 방지)
data/rfp_pages.json  감시 페이지 본문 기준선 (변경 감지용)
rfp/watchpage.py     감시 페이지 변경 감지
rfp/deadline.py      공고문에서 마감일 추정
rfp/attach.py        HWP/PDF 본문 추출
rfp/detail.py        상세·첨부 열기
data/rfp_watch.log  실행 기록
리포트/YYYY-MM-DD.html
```

## 사이트를 하나 더 붙이려면

`rfp/sites/` 에 파일을 하나 만들고 `SITE` 와 `collect(page, goto)` 만 정의한 뒤
`config.ENABLED_SITES` 에 id를 추가하면 됩니다. 목록 구조가 단순하면
`rfp.board.simple_list()` 를 쓰면 몇 줄로 끝납니다 (`atla.py` 참고).

## 사이트가 개편되면

해당 사이트만 `--show` 로 돌려 보면 브라우저 창에서 어디가 바뀌었는지 보입니다.

```
python rfp_watch.py --site krit --show
```

수집이 실패한 사이트는 리포트 맨 아래 '수집 실패' 표에 이유가 남고,
나머지 사이트는 정상적으로 계속 수집됩니다.
